# Execution Brief — OpenBot

> Generated by the `prototype-anything` skill. Specification document: any
> execution model should be able to start Stage 1 without re-asking "what is
> OpenBot".

## Summary

OpenBot is a lightweight layer that runs **inside** existing AI harnesses
(starting with DeepSeek Harness — DSH) to create and manage **bots**: each bot
is a portable `openbot.yaml` manifest with **personality, instructions, tools
and tasks**. A thin per-harness runner reads the manifest and executes the bot
in the harness's native loop, without reimplementing an agent.

**MVP:** DSH runner (skill `openbot`) + guided create/edit flow (the "simple
UI") + a *code-reviewer* example bot validated end-to-end, starting with a
**task agent** (1 execution → result).

## 1. Meta
- name: OpenBot
- version: 0.1
- domain: web-app (data-ai / agent-orchestration component)
- execution model: model-neutral (DSH first; adapter interface defined for others)

## 2. Vision & goal
- **One line:** create and manage bots (personality + instructions + tools +
  tasks) as portable manifests that run inside existing AI harnesses.
- **Success criteria:**
  1. A dev writes `openbot.yaml` (code reviewer) and runs it in DSH, receiving a
     review report.
  2. A non-technical user creates a simple bot via the guided flow, **without**
     editing YAML.
  3. The schema is harness-independent (the adapter interface is specified even
     if only DSH is implemented in the MVP).
- **Why now:** eliminate the rework of redefining personality/instructions/tools
  per use, and reuse mature harnesses instead of building another runtime.

## 3. Users & personas
- **Primary — technical author:** developer/operator who defines bots via
  manifest (persona, instructions, tools, tasks).
- **Secondary — non-technical user:** runs, monitors and edits bots via a guided
  (conversational) flow, without writing YAML.
- **Not a user (yet):** those orchestrating many bots or distributing bots in a
  marketplace.

## 4. Scope
- **In scope (MVP):** manifest schema v1; DSH runner (skill `openbot`) in task
  mode; guided create/edit flow; 1 example bot (code reviewer); manifest
  validation; adapter interface specification.
- **Out of scope (MVP):** implemented chat/scheduled/api modes; harnesses beyond
  DSH; multi-bot orchestration; marketplace/distribution; persistent
  conversation memory; a separately served web app.

## 5. Functional requirements
- **FR-1** — As a technical author, I define a bot in `openbot.yaml` (name,
  persona, instructions, tools, tasks).
  - Given a valid manifest, the runner loads it without asking for extra data.
- **FR-2** — As an author, I run a bot in task mode and receive a result.
  - Given a task, the runner executes it and returns an artifact/report.
- **FR-3** — As an author, I declare the bot's tools (native harness tools
  and/or MCP servers) and the runner wires them.
  - Given a manifest with `tools`, the bot uses only the declared tools.
- **FR-4** — As a non-technical user, I create a bot via a guided flow that
  generates the manifest without me writing YAML.
  - Given a completed flow, a valid `openbot.yaml` exists.
- **FR-5** — As a non-technical user, I edit an existing bot via the same flow.
  - Given an edit, it is reflected in the manifest and validated.
- **FR-6** — As any user, I can see the history/result of runs.
  - Given a run, it records status, result and timestamps.
- **FR-7** — The runner validates the manifest before running.
  - Given an invalid manifest, the runner reports an actionable error (field + reason).

## 6. Non-functional requirements
- **NFR-1** — Runs inside DSH, with no additional server/process.
- **NFR-2** — Manifest is pure YAML/JSON and portable (no required code).
- **NFR-3** — Reuses the harness's model and tool routing (does not reimplement).
- **NFR-4** — The guided flow speaks the user's language.

## 7. UX & design direction
- **Visual:** the "UI" is the harness's own conversational interface + a guided
  form-like question flow.
- **Main flows:** list bots → create/edit (guided flow) → run bot → see result.
- **Tone:** direct and technical in the manifest; welcoming in the guided flow.

## 8. Data & domain model
- **Entities:** `Bot` {name, version, description, persona, instructions[], tools[], tasks[], execution} · `Task` {id, kind, prompt, inputs, output} · `Run` {bot, task, status, result, startedAt, finishedAt}.
- **Relationships:** Bot *has* many Tasks; Bot *has* many Runs.
- **Storage:** manifests in `bots/*.yaml` in the workspace; runs in a local JSONL
  log per bot (e.g. `bots/<name>.runs.jsonl`).

## 9. Technical constraints & stack
- Manifest in **YAML** (JSON accepted).
- DSH runner = **skill `openbot`** (SKILL.md + references, like REA).
- No own backend; reuses the harness.

## 10. Risks & mitigations
- **"Inside the harness" + "simple UI" conflict** → the UI is the guided flow in
  the harness interface (not a separate web app).
- **Schema evolves with modes** → version it (v1) + validate.
- **Runner-skill depends on non-deterministic agent behavior** → validate the
  manifest + precise instructions; evolve to a code plugin if needed.
- **Real portability needs adapters** → specify the adapter interface now,
  implement only DSH.

## 11. Assumptions
- MVP runner = **skill** (markdown); a Cordis code plugin is an optional evolution.
- A bot runs in one harness at a time (no cross-harness orchestration in the MVP).
- Tools = subset of native harness tools + declared MCPs.
- Manifest in YAML (JSON also accepted).

## 12. Open questions
- None blocking for the MVP. (Later-stage items — chat/scheduled/api, other
  harnesses, orchestration, distribution, memory — are in the backlog.)

## 13. Definition of done
FR-1..FR-7 and NFR-1..NFR-4 pass their criteria; the code reviewer runs
end-to-end in DSH and produces a report; a non-technical user creates a bot via
the guided flow.

## Annex A — `openbot.yaml` schema v1 (draft)

```yaml
name: code-reviewer            # required, kebab-case
version: "0.1"                 # required
description: "Reviews diffs with a focus on bugs and security"  # optional
persona:                       # required — personality / system prompt
  role: "Senior code reviewer"
  tone: "direct, constructive, no fluff"
  constraints:
    - "Never suggest changes outside the diff"
instructions:                  # required — standing guidelines
  - "Review correctness, security and readability"
  - "Report blocking issues first, then suggestions"
tools:                         # optional — tools the bot may use
  harness:                     # allowlist of native harness tools
    - read
    - grep
    - glob
  mcp:                         # MCP servers to attach
    - github
tasks:                         # required — what the bot does
  - id: review-diff
    kind: task                 # task | chat | scheduled | api (MVP: task)
    prompt: "Review the staged diff and return a prioritized report"
    inputs:
      diff_path: "./diff.patch"
    output: "review-report.md"
execution:
  mode: task                   # MVP: task
  memory: none                 # MVP: none
```

## Model execution notes

- **Model-neutral (default):** use the Markdown structure above as-is.
- **Claude:** wrap the brief sections in tags (`<requirements>`, `<scope>`,
  `<task>`) and put the command in `<task>`.
- **o-series / DeepSeek-R1:** keep the system prompt minimal; do not request
  step-by-step reasoning.
- **Open models (Llama/Qwen):** feed one stage at a time.
